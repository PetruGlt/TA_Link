Task4 (sql/t4_recent_queue_status_updates.sql, output/CSVs/recent_queue_status_updates.csv):
    - first try: (sql/old/)
        - I first thought is enough to only search for daily updates up to the timestamp, but account with id 37924 has no daily updates data. Only monthly snapshots.
        - account with id 82007 and 35504 proved me wrong about the daily-first logic
            - 35504: most recent daily update is on 2025-10-06 with (queue = "OTHER",status = "ARCHIVED"). But, the monthly_reports show 
	      that at the end of October (202510) the Queue="LEGAL" and Status="LEG VERIF 2". Therefore, the monthly update is newer than the daily update.
            - Same with the account 82007, last daily_update is on 2025-09-22: queue = "OTHER" and status = "ARCHIVED". 
	      The end of the month status for October is newer and updates the queue to "COLLECTIONS" and STATUS to "PRIME_D"

        - to fix this I can:
             1. Update the query
             2. Refactor the monthly status update, and convert each year-month combination into a real timestamp (ex. 202511 -> '2025-12-01 00:00:00')

        I chose option 2 (visible in sql/t4_recent_queue_status_updates.sql < commented "-- FIX"):
            - I chose to convert each year-month into a timestamp: snapshot_ts is equal to the first moment of the following month.
                202511 -> 2025-12-01 00:00:00. This is a derived column, raw values remaining untouched. This approach respects the description of 
		the monthly snapshots given in the technical assessment description, which states: "Snapshot of latest state at the <end of each month>
		for all active accounts from the first daily update up to the respective month."

        - last_change_datetime on monthly_status is null because the data from this table does not represent the exact timestamp of the state update. 
	  In order to avoid null values I will insert the last_known_daily_update field (representing the latest change of queue or/and state) 
	  from daily_states and add the state_as_of field representing the most recent known change of date from monthly_updates. 
	  This indicates that the update happened between the interval represented by last_known_daily_change and state_as_of, 
	  without knowing the exact timestamp of the update.
